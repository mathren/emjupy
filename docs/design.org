* =emjupy= design
** Architecture

emjupy speaks to a Jupyter server the way the browser does: HTTP for
files and kernels, WebSockets for a kernel's messages and the language
server's.  Everything goes over the server's one port, so a remote
server needs one SSH tunnel and nothing started on the far side.

#+begin_example
 Emacs, on this machine                         Jupyter server, here or remote
┌─────────────────────────────────────┐        ┌───────────────────────────────────────┐
│ notebook buffer       (emjupy-mode) │  HTTP  │ Contents API ──── .ipynb files        │
│   cells ⇄ structs ⇄ .ipynb JSON ────┼───────▶│ Sessions and Kernels APIs             │
│     │ outputs, widget controls      │        │                                       │
│     ▼                               │   WS   │                          ZMQ          │
│   kernel connection ────────────────┼───────▶│ /api/kernels/…/channels ──▶ kernel    │
│                                     │   WS   │                                       │
│ shadow buffer (.py) ◀── Eglot ──────┼───────▶│ /lsp/ws/… ── jupyter-lsp ──▶ pylsp    │
│                                     │        │                                       │

└─────────────────────────────────────┘
   the bridge relays a widget page's messages over the
   kernel connection above

- The *notebook buffer* is the notebook: cells drawn as text, kept in
  step with the cell structs, which are what is saved as =.ipynb=.
- The *kernel connection* carries execution and its output; widgets'
  messages too.
- The *shadow buffer* is every code cell as one Python file, for Eglot,
  whose language server runs beside the kernel through =jupyter-lsp=.
- The *figure window* shows what a text buffer cannot -- plotly figures,
  widgets that draw themselves -- and a widget's page talks back through
  the *bridge*, a WebSocket server in Emacs, not to the Jupyter server.

Which file holds what, and the graph of their dependencies, are in
[[file:reading-the-code.org][Reading the code]].

** The shadow buffer

A notebook is not valid Python but JSON holding cells: *n* Python
fragments with prose between, a name defined in cell 3 used in cell 7.
Handed one cell at a time, a language server would see unrelated files.
So =emjupy= keeps a *shadow buffer*: one Python file of every code cell
in order, each after a marker comment naming its cell -- one module, as
=eglot= expects.

It is hidden, a well-formed document for the language server.  =C-c '=
shows it, to edit several cells at once; =C-c C-c= there writes the
changes back into the cells.  What needs the server is delegated there,
at the matching position:

- completion and eldoc, through =completion-at-point-functions= and
  =eldoc-documentation-functions=;
- =M-.= and friends, through an xref backend forwarding to =eglot='s and
  mapping the answers back onto cells;
- =eglot-rename= and the other =eglot= commands, advised to run there and
  pull their edits back.

Holding every cell, it does more than work around: a rename fixes
references in *all* cells, and =M-.= on a call in one cell lands on its
definition in another.

** The language server beside the kernel

The language server must run where the kernel does: only there can it see
your modules and the Python the code runs against.  =emjupy= talks to it
as JupyterLab does, through =jupyter-lsp= on the Jupyter server, over a
WebSocket on the notebook's connection -- so through the same SSH tunnel,
with nothing started remotely by hand.

The shadow file stays here -- beside a local notebook, in a temporary
directory otherwise -- and nothing remote reads it.  Its contents go over
the socket as the LSP document, every path rewritten in flight between
the shadow's directory and the kernel's working directory, so the server
resolves =import mylib= beside the notebook; it is also told that
directory, as where to look for modules.

When that server cannot be reached, =emjupy= falls back to one on this
machine; the cost is in [[file:language-server.org][Language server support]].

** Mapping positions

Point in a cell maps to the shadow buffer as its cell's marker plus the
offset within the cell; results map back the other way, =xref= results
inside the shadow rewritten into notebook positions.

Any other location is a file on the kernel's machine, when the server
beside the kernel answered, named there over TRAMP, the host from
=emjupy-remote-root= or the SSH tunnel.  The local fallback's paths name
this machine's files, and are left alone.

** Output

Output arrives as messages on the kernel's WebSocket, each naming its
request.  A request is finished when both its reply, on the shell channel,
and the status after its last output, on iopub, have come: the protocol
does not order the channels, so an output can follow its reply.

Stream text continues its output: consecutive text on one stream is one
output, and text on a stream whose line is still open -- no newline yet
-- continues that line even if the other stream wrote between.  That is a
terminal's rule, which progress bars rely on, each update starting with a
carriage return, applied as a terminal would.

How wide output is drawn, and when the kernel is told the width, is in
[[file:usage.org][Using a notebook]].

Output is redrawn at most a few times a second, and only in its own
cell.  A stream only grown at its end has just the new text drawn, so an
update costs what it adds, not what the output holds -- when nothing
drawn can look different: the same outputs, the stream grown at its end,
the same width, a whole line last drawn, and no carriage return or colour
escape in it, as those rewrite what came before.  Anything else redraws
the cell's output box.  Either way only that box is marked read-only
again.

* Closing a notebook

Killing a notebook's buffer closes what it opened: its kernel connection,
its language-server connection and its shadow buffer.  The kernel keeps
running on the server, by design, for the next login to adopt.  A
language server another notebook uses stays.

The connection is ended directly: the shadow buffer killed first, which
is how Eglot closes the document; the server marked as shut down on
purpose, or Eglot would start a replacement; its pending requests
dropped; and it is taken out of Eglot's table at once, so a notebook
opened a moment later is not handed it.  Nothing waits: closing takes no
measurable time.

* Redrawing

Most changes redraw only what they affect: output arriving, running a
cell (clearing its output first), inserting, deleting, splitting, merging
and moving cells, hiding and clearing output.  The rest of the buffer
moves by a known amount, so what holds a position there -- markers,
other windows, =multiple-cursors='s fake cursors -- stays.

A few redraw the whole notebook: changing a cell's type,
=emjupy-re-render=, rendering a markdown cell, undoing a structural
change.  They erase and redraw from the cells, moving every held position
to the start.

A redraw happens whole or is put right.  Stopped partway -- by an error,
or =C-g= -- it would leave text and overlays apart, the buffer showing
what the cells do not hold, so the notebook is redrawn from its cells at
once, the error still reported.  Measuring a window keeps point, as
selecting it moves its buffer's point to the window's, and a full redraw
measures once.

As a last safeguard, after redraws, when Emacs is idle, the buffer's
structure is checked: every cell's overlay present, in order, none
overlapping, each output box after its source.  Anything wrong is put
right by a redraw, and said, for its cause to be found.  Only structure
is checked, not text, which differs while typing is unsynced, and a
redraw then would undo the typing.

* Undo

Every cell command -- inserting, deleting, moving, splitting, joining,
changing a cell's type, clearing or hiding output, yanking a cell -- is
one undo step, redo taking it forward again.  The cells are snapshotted
before the command changes anything, and undoing restores the snapshot;
restoring records the state it replaced, so redo is the same the other
way.

- The snapshot is taken first, before the command changes anything.
- It is written back into the same cell objects, not copies, as the
  notebook and other undo entries refer to them.
- While a cell command runs, no earlier entry is shifted or dropped:
  undoing the step restores exactly the text they describe, before they
  are replayed.

Undo entries hold plain positions, so a redraw that is not an undo step
-- output arriving, say -- adjusts them: entries before the change stay,
those after shift by what it moved, those inside the redrawn region go.
They are changed in place, as an undo under way replays from a shared
list, and all or nothing: every new entry is worked out first; if one
cannot be, none is changed, the entries from the region on are dropped,
and that is said.  Lost history is safe; history half shifted would make
the next undo write in the wrong places.

* Use the browser's transport, not ZMQ

=jupyter server --no-browser --port=8888= exposes:

- =GET  /api/kernels=          \rightarrow list running kernels
- =POST /api/kernels=          \rightarrow start a kernel
- =GET  /api/sessions=         \rightarrow list sessions (kernel ↔ notebook pairs)
- =POST /api/sessions=         \rightarrow create or attach a session
- =GET  /api/contents=         \rightarrow list notebooks
- =GET  /api/contents/<path>=  \rightarrow fetch notebook JSON
- =PUT  /api/contents/<path>=  \rightarrow save notebook JSON
- =WS   /api/kernels/<id>/channels= \rightarrow the Jupyter protocol over WebSocket
- =WS   /lsp/ws/<server>=      \rightarrow a language server, through =jupyter-lsp=

What every browser client (JupyterLab, Classic Notebook) uses: it works
through an =ssh= tunnel, survives reconnects, and needs only =url.el=
(built in) and =websocket.el=.
