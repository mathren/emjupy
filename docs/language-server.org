#+TITLE: Language server support
#+PREVIOUS_PAGE: remote.org
#+NEXT_PAGE: troubleshooting.org

Completion, documentation, definitions and the rest, from a language
server that sees the environment the code will run in.

* The server next to the kernel

emjupy talks LSP to the language server =jupyter-lsp= runs *on the
Jupyter server*, over that server's WebSocket -- the notebook's own
transport, and how JupyterLab's =jupyterlab-lsp= works.  So:

- *Nothing written on the remote.* Code goes in-band with =didChange=.
  The local shadow file is written once, for =eglot= to attach to.
- *No second connection.* Completion and documentation make no TRAMP,
  ssh or directory calls -- measured, zero remote filesystem operations.
  Only opening a definition on the kernel's machine uses TRAMP.
- *The right environment.* Beside the kernel, the server describes the
  packages the code will import, and =M-.= finds your own modules,
  resolved against the notebook's directory.

* Requirements
:PROPERTIES:
:CUSTOM_ID: requirements
:END:
Two packages, in the Python environment running =jupyter server=:

#+begin_src bash
pip install jupyter-lsp 'python-lsp-server[all]'
#+end_src

In a conda environment file:

#+begin_src yaml
dependencies:
  - jupyter-lsp
  - python-lsp-server
#+end_src

| Package             | Purpose                                     |
|---------------------+---------------------------------------------|
| =jupyter-lsp=         | adds the =/lsp/= endpoints to Jupyter         |
| =jupyterlab-lsp=      | JupyterLab front end; requires =jupyter-lsp=  |
| =python-lsp-server=   | the Python language server                  |

=jupyterlab-lsp= installs no language server: alone, it gives the
endpoints with nothing behind them.

* Locating the language server

=jupyter-lsp= finds a server by importing it --
=importlib.util.find_spec("pylsp")= in the interpreter running
=jupyter server= -- and starts it as =[sys.executable, "-m", "pylsp"]=.  =PATH= is
not consulted: a =pylsp= elsewhere on the machine is not found.  One
installation per server, however many notebooks it serves.

* =eglot= over the Jupyter WebSocket

Every =eglot= command works against the server beside the kernel --
rename, formatting, code actions, find-implementation, whatever =eglot=
gains next -- with nothing wired up per command.

=eglot= reaches a server through three =jsonrpc= generics, and
=jsonrpc-connection-send= dispatches on the connection class:
=emjupy-eglot-server= sends over the notebook's WebSocket.
=jsonrpc-process-connection= type-checks for a process, so an idle one
is made and ignored.

The document has two names -- the shadow file here, which =eglot=
manages, and the path the kernel sees, which the server knows -- and
every message is rewritten between them in that one place.  Completion,
eldoc, =M-.= and every other =eglot= command go to the shadow buffer,
where =eglot= is attached.

With this transport the shadow file is always local, as the server is
sent its contents; =emjupy-shadow-host= applies only to the SSH
arrangement of [[file:remote.org][Working
with a remote server]].

* =eglot= commands in a notebook

=eglot='s commands look for the server of the buffer they run in, which
for a notebook is none: =M-x eglot-rename= there fails with "No current
JSON-RPC connection".  So the commands in
=emjupy-eglot-delegated-commands= -- =eglot-rename=, =eglot-code-actions=,
=eglot-format=, the =eglot-find-*= family -- run in the shadow buffer at
the point's position, their edits pulled back into the cells.  It holds
every cell, so a rename fixes references in *all* of them.

The advice does nothing outside =emjupy-mode=; =M-x
emjupy-eglot-remove-advice= removes it.

* Jumping to definitions

=eglot= installs its =xref= backend in the shadow buffer, so emjupy adds
one in the notebook that forwards there and maps the answer back.  The
shadow buffer holding every cell, =M-.= on a call in one cell lands on its
definition in another.

** Remote =M-.= needs remote LSP

A language server reads only the files of its machine:

| Language server            | Your own modules | Standard library and packages                 |
|----------------------------+------------------+-----------------------------------------------|
| beside the kernel (remote) | found            | found -- the kernel's own                     |
| on this machine (fallback) | *not found*        | found -- but THIS machine's, not the kernel's |

For a kernel elsewhere, =M-.= into your own code needs =jupyter-lsp= and
a language server *where the kernel runs* -- see [[#requirements][Requirements]].
Without them emjupy falls back to a server on this machine, saying so,
and the standard library resolves to this machine's copy, possibly
another Python.  For a kernel here, either works.

=M-x emjupy-lsp-diagnose= says which server a notebook uses: "over the
Jupyter WebSocket" is the one beside the kernel, "a local process" the
fallback.

* Jumping into modules beside a remote notebook

A definition the server beside the kernel reports is a path on the
kernel's machine, opened there over TRAMP -- the standard library's too,
as the kernel's Python is what the code runs against.  The host is
=emjupy-remote-root='s, if it names one, or that of the SSH tunnel the
server is reached through, read from the =ssh= process here: nothing to
configure behind =ssh -L=.

With no way to reach that machine -- no tunnel, nothing configured --
emjupy names the file it could not open, and =emjupy-remote-root= as what
would reach it, rather than open a same-named file here.  Paths from the
fallback server name this machine's files, and are left as they are.

* Eglot is part of the package

=eglot= ships with Emacs 30.1, which emjupy requires, and loads with it:
the WebSocket transport inherits Eglot's connection class.  Loaded, not
started: nothing connects until a notebook asks for completion or
documentation, and =emjupy= works without a server.

* Language server requests

Requests are asynchronous: eldoc runs after every command, and a
blocking request would cost a round trip per keystroke.  Completion
answers from the previous reply, asking for the next in the background.
The handshake is asynchronous too: =jupyter-lsp= starts the server on
demand, which may take seconds, with no answers until then.  A socket
that cannot be opened is retried after =emjupy-lsp-retry-interval=
seconds.

Per-command cost, measured on a twelve-cell notebook with figures:

| Operation     | Time    |
|---------------+---------|
| cursor motion | 0.0 ms  |
| completion    | 0.1 ms  |
| eldoc         | 1.2 ms  |

* When a shadow file would describe the wrong machine

If the kernel runs where this Emacs cannot reach, and
=emjupy-shadow-host= does not say how, the shadow file and its server are
local, describing *this* machine: its interpreter and packages, none of
the modules beside the notebook.  Mostly right for ordinary Python, so the
default, but confidently wrong for anything environment-specific, so
emjupy says so once per notebook.
=emjupy-shadow-when-kernel-unreachable= nil gives no language support
instead.  =emjupy-shadow-host=, or =jupyter-lsp= on the server, gives
answers from the right machine.

* When the language server cannot be reached

In the SSH arrangement the shadow file is remote, over TRAMP, and asked
for after every command: an unreachable host would block every
keystroke.  So setup gets =emjupy-shadow-timeout= seconds (2) and, on
failure, is not retried for =emjupy-shadow-retry-interval= seconds (30),
saying so once -- for creating the file, and for starting the language
server, the costly half, which otherwise repeats per command when the
host has no =pylsp=.  Editing and running cells never need the shadow
buffer: only completion, eldoc and =M-.= wait for the host.

* Falling back

=emjupy-lsp-enabled= nil selects the older arrangement, needing no
=jupyter-lsp=: the language server runs on this machine, or over SSH
beside the kernel -- see [[file:remote.org][Working with a remote server]].

* Checking it from the shell

#+begin_src bash
curl -s "http://localhost:9999/lsp/status?token=YOUR_REAL_TOKEN"
#+end_src

With your real token (=YOUR_REAL_TOKEN= is refused):

| Answer                            | Meaning                                |
|-----------------------------------+----------------------------------------|
| =404= (an HTML page)                | =jupyter-lsp= is not installed           |
| ={"message": "Forbidden"}= (403)    | the token was wrong, nothing more      |
| ={"version": 2, "sessions": {...}}= | the plumbing works; read what it lists |

=sessions= names the language servers installed:

#+begin_example
{"version": 2, "sessions": {"pylsp": {"status": "not_started", ...}}}
#+end_example

An *empty* =sessions= means the plumbing is there and no language server.
=emjupy-lsp-server= (default ="pylsp"=) names the one to ask for.  emjupy
asks =/lsp/status= itself when it cannot reach a server, and says which
of the three it found.
