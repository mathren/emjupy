* Before reading: three ideas

- *The cells are the notebook; the buffer is a drawing of them.*  Each
  cell is a struct (=emjupy-cell=, in =emjupy-core.el=) holding its source
  and outputs.  The buffer shows them, one overlay per cell.  Typing
  changes the buffer; =emjupy--sync-all-cells= reads it back into the
  cells.  Saving writes the cells, never the buffer.  When the two
  disagree, the cells win: the buffer is redrawn from them.
- *The files are layers.*  Each file uses only files below it, as the
  graph on [[file:development.org][Building and development]] shows; nothing calls upward.  Where
  a lower layer needs something from a higher one, it runs a hook list
  -- =emjupy-comm-functions= and its kind -- which the higher layer joins.
- *Loading a file does nothing.*  Definitions only.  What a notebook
  buffer needs is turned on by =emjupy-mode= when the buffer starts.  So
  any side effect is found in a function, never at the top level.

* Where to start

Read in layer order, bottom up, skimming each file's =;;;;= headings
before its code.  Every file has the same shape: a commentary at the
top, its options under =;;;; Options= if it has any, then one section
per part.

* The main flows

Each flow is traced from the command a user runs, one call to the next.
Read the functions in this order and the rest of their file falls into
place around them.

** Opening a notebook
1. =emjupy-login= (notebook) asks for the server, works out its token
   with =emjupy--resolve-token=, and binds one kernel to the port with
   =emjupy--bind-server-kernel=: one port, one kernel.
2. =emjupy-open-notebook= (notebook) reads the notebook with
   =emjupy--fetch-notebook=, which parses it with =emjupy--parse-ipynb=;
   draws it with =emjupy--draw-opened-notebook=, which turns on
   =emjupy-mode= and calls =emjupy--rerender-notebook=; and connects with
   =emjupy--attach-bound-kernel=, which calls =emjupy-connect-kernel=.
3. =emjupy-connect-kernel= (kernel) opens the WebSocket.  A notebook
   without a kernel gets one from =emjupy--spawn-and-connect-kernel=,
   started through a session so it runs in the notebook's directory.

** Running a cell
1. =emjupy-execute-cell-at-point= (kernel) syncs the cells, clears the old
   output in place, builds the request with =emjupy--make-execute-request=
   and sends it with =emjupy--ws-send=.
2. Replies come to =emjupy--handle-ws-message= (kernel), the dispatcher
   for everything a kernel sends.  Each output is built by
   =emjupy--stream-output=, =emjupy--rich-output= or =emjupy--error-output=
   and goes to =emjupy--append-output-to-cell=, which merges stream text with
   =emjupy--merge-stream-output= and asks for a redraw with
   =emjupy--schedule-render=.  A request is forgotten only when both its
   reply and its closing idle have come: =emjupy--request-half-seen=.
3. Drawing runs from a timer, not inside the socket callback:
   =emjupy--redraw-pending-output= calls =emjupy--refresh-cell-output=
   (cells), which draws only the new text when it can
   (=emjupy--append-stream-output=) and the cell's output box otherwise.
   Escape codes in a stream -- progress bars -- are applied by
   =emjupy--terminal-apply= (render).

** Editing the cells
1. A structural command, =emjupy-split-cell= say (cells), wraps its work
   in =emjupy--as-one-undo-step=: it syncs, snapshots the cells, and
   records one undo step that restores them.
2. It redraws only what changed with =emjupy--redraw-cells-in-place=,
   inside =emjupy--atomic-redraw=: a redraw finishes, or the notebook is
   redrawn from its cells at once.
3. Positions in the undo history after the change are shifted by
   =emjupy--undo-adjust= (render), which knows every entry shape
   =buffer-undo-list= can hold.

** Saving
1. =emjupy-save-notebook= calls =emjupy--save-to-server=, which sends the
   request =emjupy--notebook-request= builds, after checking the file on
   the server has not changed since it was read.
2. On idle, =emjupy--idle-save= writes a recovery copy with
   =emjupy--recovery-write=, in a folder made by =emjupy--private-directory=,
   and saves to the server without waiting, with =emjupy--autosave-async=.

** Language support
1. =emjupy-start-language-support= (eglot) builds the shadow buffer with
   =emjupy--ensure-shadow-buffer= -- all code cells as one Python file,
   from =emjupy--build-shadow-content= (lsp) -- and attaches Eglot over
   the Jupyter server's WebSocket with =emjupy--eglot-connect= (lsp), or
   to a local server when the Jupyter server has no =jupyter-lsp=.
2. In the notebook, completion and eldoc go through
   =emjupy--cell-completion-at-point= and =emjupy--cell-eldoc-function=,
   both via =emjupy--cell-shadow-delegate=, which maps the position into
   the shadow buffer.  Definitions found there are mapped back to cells
   by =emjupy--xref-remap=.

** A dropped connection
=emjupy--kernel-connection-closed= (kernel) keeps the running cells and
starts =emjupy--try-reconnect=; on reconnecting,
=emjupy--adopt-kept-runs= hands the cells to the new connection, and the
server replays what they missed.

** A notebook opened through TRAMP
=emjupy-open-this-notebook= (notebook) on a TRAMP file takes the route
from TRAMP with =emjupy--ssh-route=, finds or starts a Jupyter server
there, opens a tunnel with =emjupy--open-tunnel=, and opens the notebook
on it.  How a server's files are reached in general is
=emjupy--remote-root-for= (remote).

* The hard parts

Most functions are short.  A few carry the complexity, and a change near
them deserves the slowest reading:

- =emjupy--ensure-shadow-buffer= (eglot) and its steps,
  =emjupy--retire-moved-shadow= to =emjupy--attach-plain-eglot=: where the
  shadow file lives, when it is rebuilt, and when to stop trying -- local
  and remote, with a back-off so an unreachable host cannot hang Emacs.
- =emjupy--handle-ws-message= (kernel): every message type the kernel
  sends, and which cell it belongs to.
- =emjupy--reconcile-rules= (render): the rules drawn so line numbers
  fall on code, not on the box lines.
- =emjupy--undo-adjust= (render) and =emjupy--as-one-undo-step= (cells):
  undo across redraws.  A wrong position here does not fail; it
  rewrites the wrong text.
- =emjupy--terminal-apply= (render): a small terminal emulator, for
  progress bars.

* Reading with the tools

- *The tests are the specification.*  Test names say what is promised
  -- =emjupy-test-a-running-remote-server-is-found-again= -- and the
  docstring why.  Search =test/emjupy-test.el= for the function under
  review to find what it must do.
- *The history has the stories.*  Comments say why code is as it is;
  how it came to be is in the commit messages.  =git log -L :NAME:FILE=
  shows every change to one function, with its reason.
- *Inspect a live notebook:* =M-x emjupy-debug-check-invariants= reports
  whether the buffer and the cells agree; =emjupy-report-box-geometry=
  the widths drawn at; =emjupy-lsp-diagnose= which language server
  answers and why; =emjupy-version= what is loaded, from where.
- *The dependency graph:* =make dependency-graph= draws it from the
  requires, into =html-content/=.

* Reviewing a change

- *Layers.*  No new call to a file above; =make dependency-graph= fails
  on a require against the layers.  A file requires what it uses.
- *Loading.*  Nothing new at the top level but definitions; a hook added
  is added in an =-enable= function or =emjupy-mode=.
- *The cells are the truth.*  An edit to the buffer goes through the
  cells, and a redraw through =emjupy--atomic-redraw=.
- *Undo.*  A command changing cells records one step, through
  =emjupy--as-one-undo-step=.  A redraw in place records nothing; a full
  rebuild records the one step that puts the cells back.
- *Remote.*  Nothing on the path of every keystroke -- completion,
  eldoc, redrawing -- waits on the network or calls TRAMP.
- *Layout and style.*  Options under =;;;; Options=; messages start
  =[emjupy]=; =;;;###autoload= only on entry points; lines of 80
  columns; comments give the reason.  The rest is in [[file:development.org][Building and
  development]], Style.
- *Tests.*  A behaviour changed is a test changed or added, unit and,
  if it touches a server, live; =make check= passes.
- *Docs.*  A command, an option or a behaviour a user sees is in the
  user pages.
