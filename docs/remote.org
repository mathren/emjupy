#+TITLE: Working with a remote server
#+PREVIOUS_PAGE: appearance.org
#+NEXT_PAGE: language-server.org

Running notebooks on another machine, over a tunnel or otherwise.

* Notebooks on another machine

An =.ipynb= opened through TRAMP opens on its own machine with
=emjupy-open-this-notebook=, which makes a server and a tunnel to it,
through any hops -- see [[file:usage.org][Using a notebook]].  What follows is for a server you
started and tunnelled to yourself.

Nothing needs configuring for a kernel elsewhere: it is reached over the
Jupyter server's WebSocket, and so is the language server, with
=jupyter-lsp= beside it -- see [[file:language-server.org][Language server support]].  The shadow
file stays in a temporary directory here, its contents sent over the
socket with paths rewritten to the kernel's working directory, so
completion, documentation and =M-.= into your own modules describe the
machine the code runs on.

| Kernel runs     | =jupyter-lsp= on the server | =M-.= into your modules |
|-----------------+-----------------------------+-------------------------|
| this machine    | either                      | works                   |
| another machine | installed                   | works                   |
| another machine | not installed               | no -- the fallback server here cannot see them |

** Without =jupyter-lsp=, over SSH

With no =jupyter-lsp= but SSH access, turn the WebSocket transport off
and name the host: emjupy puts the shadow file beside the notebook there,
over TRAMP, and =eglot= starts the language server there.

#+begin_src elisp
(setq emjupy-lsp-enabled nil
      emjupy-shadow-host "/ssh:box:")
#+end_src

=emjupy-shadow-host= is a host, not a path: the directory comes from the
kernel, so =/srv/nb/analysis= becomes =/ssh:box:/srv/nb/analysis=.  Unset,
the shadow file goes to a local temporary directory: =M-.= will not find
your own modules, but nothing is written to a path meaning something
else here.  It has no effect while =emjupy-lsp-enabled= is on, the shadow
file being then always local.  =emjupy-shadow-directory= overrides where
the file goes; =emjupy-shadow-beside-notebook= turns placing it beside the
notebook off.

* Tunnelled servers

A server reached through an SSH tunnel answers at =localhost=:

#+begin_src bash
ssh -L 9999:localhost:9999 box
#+end_src

so its address does not name the machine the files are on.  emjupy finds
it, in order, from:

1. =emjupy-remote-root=, if set: a complete path, used as given.
2. The address, if it names a host other than =localhost=.
3. =emjupy-ssh-host=, if set.
4. The command line of the =ssh= process forwarding the port, read with
   =ps= on this machine; the answer, none too, is kept a minute per
   port, as a reference search maps every result.

Cases 2 to 4 give only the host; the directory comes from the kernel,
which reports the notebook's own, so notebooks in different directories
of one machine resolve to different roots unaided.

Set =emjupy-ssh-host= when no =ssh= process can be found -- a tunnel made
outside Emacs by other means:

#+begin_src elisp
(setq emjupy-ssh-host "box")
#+end_src

For several servers, an alist keyed by server label:

#+begin_src elisp
(setq emjupy-ssh-host '(("localhost:9999" . "box")
                       ("localhost:8888" . "other")))
#+end_src

TRAMP cannot reuse the tunnel, which forwards the Jupyter HTTP port, not
an SSH server's.

* How the listing is ordered

Directories, notebooks, other files, then the server's kernels; within
each, most recently modified first, so this morning's notebook is not
buried among those sharing its prefix.  Kernels, with no modification
time, by name.

* Opening files from the listing

=RET= on a file in the server dashboard opens it, by what emjupy can
address:

| Condition                          | Result                     |
|------------------------------------+----------------------------|
| =emjupy-remote-root= set             | the file, writable         |
| the address names a real host      | the file over TRAMP, writable |
| server runs on this machine        | the file, writable         |
| the server's root is known         | read-only copy over HTTP   |
| none of the above                  | an error saying what to set |

The HTTP copy uses the Contents API, needing only a kernel to have
reported where the server's files are (see [[*Where the server's files are][below]]); read-only, its header
line naming the original path.

* Multiple notebooks & multiple servers

Each server owns its token and XSRF cookie; a notebook its kernel; a
kernel its WebSocket and table of requests in flight.  So several
notebooks, from several servers -- several =ssh= tunnels on different
local ports -- can be open at once.  Run =emjupy-login= once per tunnel:

#+begin_src
M-x emjupy-login RET 8888 RET     ;; tunnel to machine A
M-x emjupy-login RET 9999 RET     ;; tunnel to machine B
#+end_src

The workflow it is built around:

1. On the remote host, start a notebook kernel on port X.
2. Locally, =ssh -L X:localhost:X user@remote=.
3. =M-x emjupy-login RET X RET=.

=emjupy= adopts the kernel running behind the port, so opening a notebook
puts you in the REPL you started; a port with none gets a fresh kernel,
one with several asks which.  Each port keeps its own kernel, so several
remote sessions stay live; =C-c M-z= gives one notebook another.  Logging
in again to a known server updates its token on the same object, so its
notebooks stay valid.

=C-c M-z= marks kernels driving another open notebook =[in
use]=: two notebooks on one kernel share interpreter state, rarely what
is wanted.

Notebook buffers are named =*emjupy: PATH [SERVER]*=, as one path can
exist on two servers; the =eglot= shadow file is qualified the same way,
so two servers' =analysis.ipynb= do not clobber each other.

If a tunnel drops, the remote kernel keeps running, and emjupy reconnects
by itself, every few seconds for =emjupy-reconnect-window= seconds (30).
A tunnel emjupy opened itself, for a notebook opened through TRAMP, it
opens again, on the same port.  Opened again through a new tunnel, a notebook on
the same machine, from the server on the same port there, is the same
notebook: its buffer is reached again, its edits kept.  The same path
from a server on another port is another notebook, opened apart.
A cell running meanwhile is not lost: the server keeps the kernel's
messages and hands them to the same session reconnecting, so the cell
gets everything it printed.  A cell run while it reconnects runs once
it is back.  One whose run ended while disconnected, its
end not kept, is ended too, its output perhaps incomplete.  If the
connection does not return in time, the cells are ended, and
=emjupy-reconnect-kernel= (=C-c C-x C-c=) reconnects by hand; session
state survives either way.  =emjupy-reconnect-window= nil does not try.
A kernel the server answers it no longer has -- it died, or was shut
down -- is not waited for; a server that does not answer at all is said
to have perhaps stopped.  A kernel shut down or culled while a cell runs
on it, its connection left open, is noticed too: after
=emjupy-kernel-check-interval= seconds (30) with nothing from it, emjupy
asks the server; nil never asks.

* Access tokens

The token is resolved without asking where possible: an explicit
argument, else the server's registered token, else none -- common for
tunnelled servers started with =--IdentityProvider.token= -- and only then
a prompt.  =C-u M-x emjupy-login= always prompts.

* If the token is the problem

A tunnelled server still has a token.  emjupy remembers it per server --
=C-u M-x emjupy-status= lists each open notebook with its server -- so
it is typed again only to check the server from the shell, with =curl=
say.

* Where the server's files are
Jupyter does not publish its root directory, deliberately.  emjupy works
it out: the kernel reports the directory it runs in, the notebook's own,
and the Contents API the notebook's path relative to the root.  Take the
second off the end of the first:

#+BEGIN_SRC
 kernel cwd     /home/you/project/analysis
 notebook path  analysis/run.ipynb
 root           /home/you/project
#+END_SRC

So =emjupy-remote-root= rarely needs setting: once a notebook's kernel
starts, browsing that server's files works.  Set it when the derived
root is not wanted -- a local mirror, a path through a TRAMP hop emjupy
cannot infer -- and it takes precedence.  A kernel started outside the
notebook's folder does not line up, and emjupy says it cannot tell
rather than invent a path.

In the dashboard, =d= opens what the cursor is on: a directory in Dired,
a notebook or file as its directory, point on it.

* Recovering from a dropped connection

Suspending the machine kills a tunnelled WebSocket, and one dying
mid-render can leave the buffer unlike the cells.
=M-x emjupy-reconnect-kernel= (=C-c C-x C-c=) checks the buffer against
the cells and redraws if they differ: the cells are the notebook, the
buffer a drawing of them.  =M-x emjupy-re-render= does the same by hand.
