#+TITLE: Building & development
#+PREVIOUS_PAGE: reading-the-code.org
#+NEXT_PAGE: limitations.org

=emjupy= is a multi-file Emacs package, developed with Claude Opus 5.5
and other LLMs.  Build a tar and install it:

#+begin_src bash
make package                 # generates emjupy-i.j.k.tar
#+end_src

then =M-x package-install-file RET emjupy-i.j.k.tar
RET=, =i.j.k= being the version.

It needs Emacs 30.1+ and =websocket= (1.15+).  Installed as a package,
the commands you start from -- =emjupy-login=, =emjupy-open-notebook=,
=emjupy-server-dashboard= -- are autoloaded: no =require= needed.

* Which Emacs to develop against

Emacs 30.1: the minimum the package declares, what CI runs, what most
users have.  =make versions= says which Emacs is in use, and whether it
is the target.

=test_notebooks/=.

| =emjupy-cells.el=         | syncing, cell editing and commands, redrawing in place      |

** Dependencies run one way

No file calls or names anything defined in a file below it in the
table, and there are no =declare-function= forms for emjupy's own
functions.  Each file requires the files whose functions it uses, and
only those; each loads on its own -- =(require 'emjupy-lsp)= in a fresh
Emacs works -- which is what makes this checkable.

The graph is drawn from the code by =tools/dependency-graph.py= when the
site is built (=make dependency-graph= draws it alone), each file above
those it requires.  Lines a longer path implies are left out;
=dependencies.dot= has every require, for Graphviz.

#+CAPTION: Dependency graph of the =emjupy= package.
[[file:dependencies.svg]]

A lower layer tells a higher one something happened by running a hook:

- =emjupy-kernel-connected-functions=: a kernel attached.  =emjupy-mode=
  hangs two handlers on it: ask the kernel where it runs, for the
  language server; tell it the cell width.
- =emjupy-box-width-changed-functions=: the width cells are drawn at
  changed, so the kernel is told.
- =emjupy-comm-functions=, run with each comm message, and
  =emjupy-output-owner-functions=, asked which cell an output answering
  no cell's request belongs to.  The widgets layer keeps its models from
  the first, and claims with the second the output a moved slider
  causes.
- =emjupy-widget-view-functions=: the drawing layer asks for a widget's
  controls; the widgets layer answers.

They are wired when a notebook buffer starts -- =emjupy-mode= turns each
layer on -- not when a file loads.  Only hooks run upward; nothing is set
to one function for a layer below to call.  The rest follows from where
things are put:

- A redraw happens whole or is put right by redrawing from the cells.
  The redraws needing that -- a cell's output in place, every output on
  a width change -- are in the cells layer, so putting one right is a
  plain call.
- A key on a lower layer's map is bound by the layer whose command it
  runs: the click on hidden output in the cells layer, opening an output
  in the figures layer.
- The mode's keys and menu name commands of every layer, so
  emjupy-notebook.el, above them all, fills the map =emjupy-mode= makes.
- A widget control drawn by the widget-page layer carries the function
  that opens it, which the widgets layer calls.

** Errors

Catch the failure you expect; let the rest through.  The package has no
=ignore-errors=: it hides bugs along with the expected failure.

- A failure with a precondition is checked, not caught: =window-live-p=,
  =buffer-live-p=, =websocket-p= and =websocket-openp=,
  =jsonrpc-running-p=, =xref-file-location-p=.
- One found only by trying is caught by type: =json-error= -- the whole
  family, as too-deep nesting or non-UTF-8 bytes are a =json-error= but
  not a =json-parse-error= -- =jsonrpc-error=, =file-error=.
- A failed request to the Jupyter server signals =emjupy-http-error=, or
  =emjupy-http-status= for an error status; both are children of
  =file-error=, which keeps their messages readable.
  =emjupy--http-status-of= extracts the status; =emjupy--http-exists-p=
  returns nil for a 404 instead of signalling.
- A Contents API path goes through =emjupy--contents-path=, never a bare
  =concat=: a name can hold =#= or =?=, so =a#b.ipynb= would be asked
  for, and saved, as =a=.
- Background work that must not abort its command -- the language server
  warming up as a notebook opens -- uses =with-demoted-errors=.

** Style

Every file starts with the same header.  A Lisp file:

#+begin_src emacs-lisp
;;; emjupy-example.el --- One line saying what it is  -*- lexical-binding: t; -*-

;; Copyright (C) 2026 Mathieu Renzo

;; Author: Mathieu Renzo <mrenzo@arizona.edu>
;; Assisted-by: Claude:claude-opus-5.5 and other free-tier LLMs
;; SPDX-License-Identifier: GPL-3.0-or-later

;; This file is not part of GNU Emacs.

;;; Commentary:

;;; Code:
#+end_src

The licence is given by its SPDX identifier alone.  Python, shell and the
Makefile carry the copyright and SPDX lines as comments, after any =#!=.

The code follows the [[https://github.com/bbatsov/emacs-lisp-style-guide][Emacs Lisp style guide]]:

- Requires at the top, in one block.  An optional or heavy library --
  =xwidget=, =org= for LaTeX -- is required in the function needing it,
  with a comment saying why.
- Loading a file only defines things: hooks are added when =emjupy-mode=
  starts, the mixed-installation check runs when the first notebook
  opens.
- Emacs's own indentation, quoted data lists aligned as data; spaces, no
  trailing whitespace, no closing parentheses on a line of their own.
- =#'= for a function passed as an argument; =when= and =unless= for one
  branch; a docstring for every variable defined with a value; =;;;;=
  for a section heading.
- No code left commented out: it is in the history.
- =;;;###autoload= only on commands that make sense before emjupy is
  loaded: logging in, listing, opening, creating, the menu.
- A question takes =y-or-n-p=: one key, =y= or =n=, to answer.
- Every file in sections: user options first, under =;;;; Options=, then
  a =;;;;= heading per part.  Messages start =[emjupy]=.
- Comments say why, briefly; how the code came to be is in the history.
- Lines of 80 columns at most.  A long call breaks between arguments, or
  puts them below its name; a deep expression is better bound to a name.
  Exceptions: a string long in itself -- a URL, a regexp, JSON, a
  message someone may search for -- a file's first line, a test's name.

* Continuous integration

Each check runs once per event:

| Event                                     | Runs                                                                                                           |
|-------------------------------------------+----------------------------------------------------------------------------------------------------------------|
| pull request                              | =build-package.yml=: check (lint, the recipe compiled, package, docs), melpazoid, and the tests, unit and live |
| push to =main=                            | =build-package.yml=: check and melpazoid                                                                       |
| push to =main= changing =src/= or =test/= | and =coverage.yml=: the tests, unit and live, once, instrumented -- what fails them fails it                   |
| tag                                       | =release.yml= only                                                                                             |
| by hand                                   | =set-version.yml=, or any of the above from the Actions tab                                                    |

Everything needing only Emacs is one job, =check=.  On =main= the tests
run once, in =coverage.yml=; the timing tests, skipped there, run on pull
requests.  The release is one job, publishing nothing -- release,
tarball, site -- until all of it passes.  It tests what it ships, as the
version commit is often pushed with =[skip ci]=.

Other branches run nothing until a pull request; a newer push cancels a
run still going.  Build also runs for changes to the docs, the tools,
the notebook corpus and the MELPA recipe.

* Running everything locally

What CI runs, cheap checks first.

** Once: what the checks need

- Emacs 30.1 -- =make versions= says whether you have it.
- =websocket.el=: an installed copy is found, or name a checkout with
  =export EMJUPY_WEBSOCKET_DIR=/path/to/emacs-websocket=.
- For the integration tests, a Python environment with the server, a
  kernel and a language server:
  #+begin_src bash
  pip install jupyter-server ipykernel jupyter-lsp 'python-lsp-server[all]'
  #+end_src
- For =make lint=, package-lint: =M-x package-install RET package-lint=,
  or =PACKAGE_LINT_DIR= naming a checkout.  It runs as MELPA runs it,
  warnings failing too, and fails without package-lint or an archive
  listing the dependencies -- MELPA, or the one =EMJUPY_PACKAGE_ARCHIVE=
  names.
- For melpazoid, a clone and Docker, as it runs in a container to match
  MELPA:
  #+begin_src bash
  git clone https://github.com/riscy/melpazoid ~/melpazoid
  #+end_src

** Every time

#+begin_src bash
make compile                # no warnings expected
make test                   # unit tests, about ten seconds
make lint                   # checkdoc and package-lint: nothing expected
make check-version          # three places agree on the version
#+end_src

The integration tests, against a server of your own:

#+begin_src bash
mkdir -p /tmp/nbroot
jupyter server --no-browser --port=8888 --ip=127.0.0.1 \
  --IdentityProvider.token=abc --ServerApp.root_dir=/tmp/nbroot &

EMJUPY_TEST_URL=127.0.0.1:8888 EMJUPY_TEST_TOKEN=abc \
EMJUPY_TEST_ROOT=/tmp/nbroot make check
#+end_src

=EMJUPY_SKIP_UNSTABLE=1= leaves out tests tagged =:unstable=, as CI does.

melpazoid, reading the recipe MELPA will be sent:

#+begin_src bash
RECIPE="$(cat .github/melpa-recipe)" LOCAL_REPO="$PWD" make -C ~/melpazoid
#+end_src

Coverage needs =undercover.el= and its two dependencies, installed or
checked out:

#+begin_src bash
git clone https://github.com/undercover-el/undercover.el ~/src/undercover
git clone https://github.com/magnars/dash.el ~/src/dash
git clone https://github.com/rejeep/shut-up.el ~/src/shut-up
export EMJUPY_UNDERCOVER_PATH=~/src/undercover:~/src/dash:~/src/shut-up

make coverage               # prints a per-file table; lcov in coverage/
#+end_src

With the integration variables set it covers the server-facing code too,
as CI runs it.  Tests tagged =:timing= are left out: instrumented, time
means nothing.

The docs, with CI's link check -- every page and anchor linked to must
exist:

#+begin_src bash
make docs                   # then open html-content/index.html
python3 tools/check-links.py
#+end_src

Link to a section of another page by its =CUSTOM_ID=, and within a page
too: the site's anchors are the =CUSTOM_ID=, or else a slug of the title,
and a heading-search link =[[*Title]]= is not mapped to that slug.

=.github/melpa-recipe= must list every file the package ships.
=make recipe-check= checks it, as CI does: every file the Makefile ships
is listed, nothing listed is missing, and the recipe's files alone, in
an empty directory, byte-compile.  Run it after adding a file:

#+begin_src bash
make recipe-check
#+end_src

** Compiling one file by hand

=M-x byte-compile-file= compiles against =load-path=: with emjupy
installed from an archive, =(require 'emjupy-core)= finds the INSTALLED
copy, and a module added since is not found -- "Cannot open load file:
emjupy-remote" is that, not a fault in the file.  =make compile= puts
=src/= first; by hand, put the checkout first on =load-path=, or
uninstall the package meanwhile.

=emjupy-run-tests.el=, =emjupy-pkg.el= and =publish.el= say
=no-byte-compile=: scripts and metadata, not code to load.  Without it
for =publish.el=, an install from git with package-vc, which compiles
the whole checkout, would warn about the site's build script.

* Unit tests

The self-contained suite needs only =websocket=:

#+begin_src bash
make test
# which is
emacs -batch -Q -l test/emjupy-run-tests.el
#+end_src

=websocket= comes from =load-path=, then =EMJUPY_WEBSOCKET_DIR=, then
GNU ELPA -- so the suite runs offline too:

#+begin_src bash
EMJUPY_WEBSOCKET_DIR=/path/to/emacs-websocket make test
#+end_src

* Integration tests (real server, real kernel, real LSP)

=emjupy-integration-test.el= runs real Python in a real kernel on a live
Jupyter server.  Opt-in: they =ert-skip= unless the environment names a
running server.  They catch what only a live server shows -- an image
this Emacs cannot display, a WebSocket URL dropping its base path, a
saved notebook no other tool opens.

| Variable             | Meaning                                                     |
|----------------------+-------------------------------------------------------------|
| =EMJUPY_TEST_URL=    | =host:port= of a running server (the LOCAL end of a tunnel) |
| =EMJUPY_TEST_TOKEN=  | its token                                                   |
| =EMJUPY_TEST_ROOT=   | server root dir, for the nbformat-validation test           |
| =EMJUPY_TEST_URL2=   | a SECOND server, for the multi-server tests                 |
| =EMJUPY_TEST_TOKEN2= | its token (defaults to =EMJUPY_TEST_TOKEN=)                 |

For the *remote* path, point =EMJUPY_TEST_URL= at the local end of an ssh
tunnel:

#+begin_src bash
# server side: jupyter listens only on loopback
jupyter server --no-browser --port=8888 --ip=127.0.0.1 --IdentityProvider.token=abc

# client side: forward a local port through ssh
ssh -N -L 18888:127.0.0.1:8888 user@remote-host &

EMJUPY_TEST_URL=127.0.0.1:18888 EMJUPY_TEST_TOKEN=abc \
EMJUPY_TEST_ROOT=/path/to/notebook/root make check
#+end_src

The WebSocket language-server tests need =jupyter-lsp= and
=python-lsp-server= where the server runs (the =pip= line above).  Those
of the local fallback need a server on this machine's =PATH= (=pylsp=,
=pyright-langserver= or =jedi-language-server=), and skip without one.

* Robustness tests

=test/emjupy-robustness-test.el= holds tests making their own inputs.
They run with =make test=; each found a bug the hand-written ones missed.

| Test            | What it tries                                            |
|-----------------+----------------------------------------------------------|
| message order   | random interleavings of a kernel's replies and outputs   |
| random edits    | random sequences of cell commands, invariants after each |
| undo everything | random edits, then undo to the start                     |
| round-trip      | every notebook in =test_notebooks/test-corpus/=, saved and reloaded |
| hostile content | escape floods, huge SVGs, deep JSON, awkward file names  |
| leaks           | many sessions; timers, processes, hooks, tables after    |

** Seeds

Every failure of a randomised test names its run's seed:

#+begin_src
Info: EMJUPY_FUZZ_SEED=4, case 5
Info: after (insert-above insert-below delete-char split move-down)
#+end_src

Set it to replay the run; =EMJUPY_FUZZ_ITERATIONS= sets the cases per
test, by default ten to two hundred:

#+begin_src bash
EMJUPY_FUZZ_SEED=4 EMJUPY_FUZZ_ITERATIONS=500 make test
#+end_src

Shrink a failing sequence before working on it: drop a step, and keep
the drop while it still fails.

** Expected failures

A test of a known, unfixed fault is marked =:expected-result :failed=,
the reason in its docstring: the suite stays green, the fault visible,
and a fix shows as an unexpected pass -- the cue to unmark it.

** The notebook corpus

=test_notebooks/test-corpus/= is written by =tools/make-notebook-corpus.py=
with =nbformat=, so each notebook is valid by Jupyter's own definition.
=tools/check-roundtrip.py= compares a notebook with emjupy's save of it
-- cells, sources, outputs, metadata, attachments -- and validates the
save; without =nbformat=, the round-trip test checks only that saving
twice changes nothing.  Add a new shape to the generator, not by hand.
It gives each cell the same id every run, so it changes nothing unless
the generator did; CI fails if the committed corpus differs from what it
writes.

The notebooks beside it, to try emjupy on, are kept without outputs;
CI checks with =nbstripout
--verify=.  =nbstripout --install= has git strip them as they are
committed -- =.gitattributes= names them, not the corpus, whose outputs
are what it tests.

** Network faults

=tools/faultproxy.py= sits between emjupy and the server and, on command,
drops connections, stalls, delays or splits what it forwards.  The
=emjupy-int-fault-*= tests start it in front of the test server, so need
=python3=.  By hand:

#+begin_src bash
python3 tools/faultproxy.py 127.0.0.1 8888     # prints its port and control port
echo stall | nc 127.0.0.1 CONTROL-PORT         # or sever, resume, delay 200, chunk 7, reset
#+end_src

** Compiled files

Emacs loads a =.elc= before its =.el=, newer or not.  To see a test fail
without a fix, =make clean= first, or the test runs the compiled old code.

* Test hygiene

A unit test must give the same answer on every machine.  Two detections
would vary: an SSH tunnel's host, read from the process list, and
whether LaTeX renders, from the programs installed.
=emjupy-probe-environment= governs both; the unit test runner binds it
to nil, and a test of the detection itself binds it to t and stubs what
it examines.

- Test the key binding, not only its command: one bound to =DEL= alone
  is not reached in a graphical Emacs, which sends =<backspace>=.
- Do not wrap the action tested in =ignore-errors=: the error it
  swallows may be the failure.
- A stub of a function Emacs itself uses calls through for the cases the
  test is not about.
- Assert invariants rather than mechanisms, which differ between Emacs
  versions.

* Invariants

=M-x emjupy-debug-check-invariants= reports how a buffer and its cells
disagree: for which cell, an overlay missing, overlapping, out of order,
detached from its output box, or showing text the cell does not hold --
what is displayed and what would be saved come apart.  Tests call it
after every operation.

* Performance

Three tests guard against regressions, not speed:

- work after every command does not grow with the notebook;
- redrawing output does not either: only the cell concerned is redrawn;
- nothing on a path run after a command touches a remote file.

The last matters most: TRAMP blocks Emacs for a round trip, paid on every
keystroke if on the per-command path.  The test asserts no such calls,
not a duration, which would depend on a network.  The costs kept small
are measured in [[file:language-server.org][Language server
support]].

* Releasing

1. *Set the version.*  On GitHub: Actions, "Set version", "Run workflow",
   with the new version as =X.Y.Z=.  It writes it everywhere the current
   one is -- the =;; Version:= header, =emjupy-version=,
   =src/emjupy-pkg.el=, the sample in =docs/usage.org= -- checks they
   agree, and commits.  Locally: =make set-version X.Y.Z=.
2. *Tag that commit* with the version and push the tag: the release runs
   the tests, puts the tarball on the release page and publishes the
   site, all from that commit.  Tag it yourself: a tag a workflow pushes
   starts no other workflow.  A commit message with =[skip ci]= skips
   tag pushes too, so tag a commit without it.

* The package's own description

=C-h P emjupy= shows the =;;; Commentary:= of =src/emjupy.el=: what
emjupy is, what it needs, how to start -- for someone who has just
installed it.  package.el would show a README instead, a web page of
badges and links, so =make package='s tarball has none, as MELPA's
does not.  A =package-vc= install, the whole checkout, shows the README.

The opening paragraph is the same in the Commentary, the README and
=docs/index.org=; keep it so.  The one-line summary is the same in
=src/emjupy.el='s header and =src/emjupy-pkg.el=.

* Submitting to MELPA

The recipe lists its files: they are in =src/=, where MELPA's default
=:files= does not look, and by name, so a development file added there
does not ship.  The tests, in =test/=, are not shipped.  It is kept at
=.github/melpa-recipe=, which the melpazoid job reads too:

#+begin_src elisp
(emjupy :fetcher github
        :repo "mathren/emjupy"
        :files ("src/emjupy.el"
                "src/emjupy-core.el"
                "src/emjupy-http.el"
                "src/emjupy-render.el"
                "src/emjupy-cells.el"
                "src/emjupy-kernel.el"
                "src/emjupy-figures.el"
                "src/emjupy-widgets.el"
                "src/emjupy-widget-page.el"
                "src/emjupy-figure-window.py"
                "src/emjupy-remote.el"
                "src/emjupy-lsp.el"
                "src/emjupy-eglot.el"
                "src/emjupy-mode.el"
                "src/emjupy-notebook.el"))
#+end_src

Before submitting:

#+begin_src bash
make check                 # unit and integration tests
make lint                  # checkdoc and package-lint
make package               # builds the tar
#+end_src

and check that:

- melpazoid reports nothing -- its CI job runs it on the recipe above,
  warnings as errors;
- the tar installs into an empty =package-user-dir= and =M-x
  emjupy-mode= works there;
- each module loads on its own in a fresh Emacs, which shows an
  accidental dependency on load order.
