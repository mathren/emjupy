#+TITLE: Building & development
#+PREVIOUS_PAGE: reading-the-code.org
#+NEXT_PAGE: limitations.org

=emjupy= is a multi-file Emacs package, developed with Claude Opus 5.5
and other LLMs.  Build a tar and install it:

#+begin_src bash
make package                 # generates emjupy-i.j.k.tar
#+end_src

then =M-x package-install-file RET emjupy-i.j.k.tar
RET=, =i.j.k= being the version.

emjupy needs Emacs 30.1 or later, and =websocket= 1.15 or later.  When
it is installed as a package, the commands you start from are
autoloaded, so no =require= is needed.  They are =emjupy-login=,
=emjupy-open-notebook= and =emjupy-server-dashboard=.

* Which Emacs to develop against

The target is Emacs 30.1: it is the minimum the package declares, what
CI runs, and what most users have.  =make versions= says which Emacs is
in use, and whether it is the target.

* Source layout

The sources are in =src/=, one layer per file, and each file requires
only those below it.  [[file:reading-the-code.org][Reading the code]]
lists them in that order, says what each holds, and draws the graph of
their requires.  =emjupy-pkg.el= is the package metadata for
=make package= (MELPA makes its own).  =emjupy-figure-window.py= is the
window that interactive figures open in, and ships with the sources.
The tests are in =test/=.  The unit tests of each file are in
=emjupy-FILE-test.el=, and what they share is in
=emjupy-test-helpers.el=.  The notebooks they read are in
=test_notebooks/=.

* Code rules

** Dependencies run one way

No file calls or names anything defined in a file below it in the table.
A keymap is the exception: it names its commands wherever they are
defined, with a plain quote.  A binding is resolved when the key is
pressed, and a keymap reads best whole.  There are no =declare-function=
forms for emjupy's own functions.  Each file requires the files whose
functions it uses, and only those.  Each file loads on its own:
=(require 'emjupy-lsp)= works in a fresh Emacs.  That is what makes the
rule checkable.

The graph of these requires is in [[file:reading-the-code.org][Reading
the code]].  =tools/dependency-graph.py= draws it from the code when the
site is built; =make dependency-graph= draws it alone.
=dependencies.dot= has every require, for Graphviz.

A lower layer tells a higher one something happened by running a hook:

- =emjupy-kernel-connected-functions= runs when a kernel attaches.
  =emjupy-mode= puts two handlers on it.  One asks the kernel where it
  runs, for the language server.  The other tells it the cell width.
- =emjupy-box-width-changed-functions=: the width cells are drawn at
  changed, so the kernel is told.
- =emjupy-comm-functions= runs with each comm message.
  =emjupy-output-owner-functions= is asked which cell owns an output
  that answers no cell's request.  The widgets layer keeps its models
  from the first.  With the second, it claims the output that a moved
  slider causes.
- =emjupy-widget-view-functions=: the drawing layer asks for a widget's
  controls; the widgets layer answers.

They are wired when a notebook buffer starts -- =emjupy-mode= turns each
layer on -- not when a file loads.  Only hooks run upward; nothing is
set to one function for a layer below to call.  The rest follows from
where things are put:

- A redraw either completes, or is repaired by redrawing from the cells.
  The redraws that need this are in the redraw layer: a cell's output in
  place, and every output on a width change.  So repairing one is a
  plain call.
- Undo is in two files, on purpose: [[file:reading-the-code.org][Reading the code]] says why.
- A keymap is defined whole where it is made.  The output maps are in
  the drawing layer, the mode's map is in emjupy-mode.el, and the menu
  is in emjupy-notebook.el.
- A widget control drawn by the widget-page layer carries the function
  that opens it, which the widgets layer calls.

** Errors

Catch the failure you expect; let the rest through.  The package has no
=ignore-errors=: it hides bugs along with the expected failure.

- A failure with a precondition is checked, not caught.  The checks are
  =window-live-p=, =buffer-live-p=, =websocket-p= and =websocket-openp=,
  =jsonrpc-running-p=, and =xref-file-location-p=.
- A failure found only by trying is caught by its type: =json-error=,
  =jsonrpc-error= or =file-error=.  Catch =json-error=, the whole
  family: too-deep nesting and non-UTF-8 bytes are a =json-error= but
  not a =json-parse-error=.
- A failed request to the Jupyter server signals =emjupy-http-error=, or
  =emjupy-http-status= for an error status.  Both are children of
  =file-error=, which keeps their messages readable.
  =emjupy--http-status-of= extracts the status.  =emjupy--http-exists-p=
  returns nil for a 404 instead of signalling.
- A Contents API path goes through =emjupy--contents-path=, never
  through a bare =concat=.  A name can hold =#= or =?=, so =a#b.ipynb=
  would otherwise be requested, and saved, as =a=.
- Background work that must not abort its command -- the language server
  warming up as a notebook opens -- uses =with-demoted-errors=.

** Style

Every file starts with the same header.  A Lisp file:

#+begin_src emacs-lisp
;;; emjupy-example.el --- One line saying what it is  -*- lexical-binding: t; -*-

;; Copyright (C) 2026 Mathieu Renzo

;; Author: Mathieu Renzo <mrenzo@arizona.edu>
;; Assisted-by: Claude:claude-opus-5.5 and other free-tier LLMs
;; SPDX-License-Identifier: GPL-3.0-or-later

;; This file is not part of GNU Emacs.

;;; Commentary:

;;; Code:
#+end_src


The licence is given by its SPDX identifier alone.  Python, shell and the
Makefile carry the copyright and SPDX lines as comments, after any =#!=.

The code follows the Elisp manual's
[[https://www.gnu.org/software/emacs/manual/html_node/elisp/Tips.html][Tips
and Conventions]] and the
[[https://github.com/bbatsov/emacs-lisp-style-guide][Emacs Lisp style
guide]].  That means: requires and compiler declarations at the top,
Emacs's own indentation, =#'= for a function that is passed, =when= and
=unless= for a single branch, a docstring for every variable with a
value, no commented-out code, and lines of 80 columns.  emjupy adds its
own rules:

- Loading a file only defines things.  Hooks go in a layer's =-enable=
  function, which =emjupy-mode= calls.  An optional or heavy library,
  such as =xwidget= or =org= for LaTeX, is required where it is needed.
  It is declared at the top, with a comment that says why.
- A keymap is a =defvar= whose value builds it whole, never a
  =define-key= at top level.
- =;;;###autoload= only on commands that make sense before emjupy is
  loaded: logging in, listing, opening, creating, the menu.
- A question takes =y-or-n-p=.
- No advice on another package's functions, but on Eglot's commands:
  =emjupy-eglot.el= says why.
- Every file in sections: user options first, under =;;;; Options=, then
  a =;;;;= heading per part.  Messages start =[emjupy]=.
- A user option goes in its subject's group, defined in emjupy-core.el.
  It is =:safe= only if it changes nothing but how a notebook looks or
  is exported.  An option that runs a program, loads code, or reaches a
  file or host is never =:safe=.
- Comments say why, briefly.
- A line goes past 80 columns only for a string that is long in itself
  (a URL, a regexp, JSON, a message someone may search for), for a
  file's first line, or for a test's name.

** Words for what is on screen

Function names keep four verbs apart:

- /draw/: put into the buffer what is not there yet -- a cell, its output,
  a widget (=emjupy--draw-cell=);
- /redraw/: replace what is drawn, in place (=emjupy--redraw-cell-output=,
  =emjupy--redraw-notebook=, every cell);
- /render/: turn data into what is drawn -- faces, an image -- touching no
  buffer (=emjupy--render-ansi=);
- /refresh/: fetch again what may have changed elsewhere -- on the server,
  in the kernel, the theme (=emjupy-list-refresh=).

The drawing layer is still called =emjupy-render.el=, and two commands
keep the names users know.  =emjupy-re-render= redraws the notebook.
=emjupy-refresh-appearance= re-reads the theme and redraws.

* Continuous integration

Each check runs once per event:

| Event                               | Runs                                                                                                         |
|-------------------------------------+--------------------------------------------------------------------------------------------------------------|
| pull request                        | =build-package.yml=: check (lint, the recipe compiled, package, docs), melpazoid, and the tests, unit and live |
| push to =main=                        | =build-package.yml=: check and melpazoid                                                                       |
| push to =main= changing =src/= or =test/= | and =coverage.yml=: the tests, unit and live, once, instrumented -- what fails them fails it                   |
| tag                                 | =release.yml= only                                                                                             |
| by hand                             | =set-version.yml=, or any of the above from the Actions tab                                                    |

Everything that needs only Emacs is one job, =check=.  On =main= the
tests run once, in =coverage.yml=.  The timing tests are skipped there,
and run on pull requests.  The release is one job.  It publishes nothing
(release, tarball, site) until all of it passes.  It tests what it
ships, because the version commit is often pushed with =[skip ci]=.

Other branches run nothing until a pull request; a newer push cancels a
run still going.  Build also runs for changes to the docs, the tools,
the notebook corpus and the MELPA recipe.

* Running everything locally

What CI runs, cheap checks first.

** Once: what the checks need

- Emacs 30.1 -- =make versions= says whether you have it.
- =websocket.el=: an installed copy is found, or name a checkout with
  =export EMJUPY_WEBSOCKET_DIR=/path/to/emacs-websocket=.
- For the integration tests, a Python environment with the server, a
  kernel and a language server:
  #+begin_src bash
  pip install jupyter-server ipykernel jupyter-lsp 'python-lsp-server[all]'
  #+end_src
- =make lint= needs package-lint:
  =M-x package-install RET package-lint=, or =PACKAGE_LINT_DIR= naming a
  checkout.  It runs as MELPA runs it, so warnings fail too.  It fails
  without package-lint, and without an archive that lists the
  dependencies: MELPA, or the one =EMJUPY_PACKAGE_ARCHIVE= names.
- melpazoid needs a clone and Docker, because it runs in a container to
  match MELPA:
  #+begin_src bash
  git clone https://github.com/riscy/melpazoid ~/melpazoid
  #+end_src

** Every time

#+begin_src bash
make compile                # no warnings expected
make test                   # unit tests, about ten seconds
make lint                   # checkdoc and package-lint: nothing expected
make check-version          # three places agree on the version
#+end_src

The integration tests, against a server of your own:

#+begin_src bash
mkdir -p /tmp/nbroot
JUPYTER_TOKEN=abc jupyter server --no-browser --port=8888 --ip=127.0.0.1 \
  --ServerApp.root_dir=/tmp/nbroot &

EMJUPY_TEST_URL=127.0.0.1:8888 EMJUPY_TEST_TOKEN=abc \
EMJUPY_TEST_ROOT=/tmp/nbroot make check
#+end_src

=EMJUPY_SKIP_UNSTABLE=1= leaves out tests tagged =:unstable=, as CI does.

melpazoid, reading the recipe MELPA will be sent:

#+begin_src bash
RECIPE="$(cat .github/melpa-recipe)" LOCAL_REPO="$PWD" make -C ~/melpazoid
#+end_src

Coverage needs =undercover.el= and its two dependencies, installed or
checked out:

#+begin_src bash
git clone https://github.com/undercover-el/undercover.el ~/src/undercover
git clone https://github.com/magnars/dash.el ~/src/dash
git clone https://github.com/rejeep/shut-up.el ~/src/shut-up
export EMJUPY_UNDERCOVER_PATH=~/src/undercover:~/src/dash:~/src/shut-up

make coverage               # prints a per-file table; lcov in coverage/
#+end_src

With the integration variables set it covers the server-facing code
too, as CI runs it.  Tests tagged =:timing= are left out: instrumented,
time means nothing.

Build the docs and run CI's link check, which requires every linked page
and anchor to exist:

#+begin_src bash
make docs                   # then open html-content/index.html
python3 tools/check-links.py
#+end_src

The Org sources are checked too, by the test suite, without building the
site.  =emjupy-test-every-link-in-the-docs-leads-somewhere= follows
every internal link to its file, and to the heading it names.

Link to a section by its title: =[[*Title]]= within a page,
=[[file:page.org::*Title]]= to another page.  There is no =CUSTOM_ID= to
manage.  The site makes each heading's anchor from the slug of its
title, and resolves title links to it.  Renaming a heading changes its
anchor, so links to it need the new title.
=python3 tools/check-links.py= finds any that do not have it.

=.github/melpa-recipe= must list every file the package ships.
=make recipe-check= checks it, as CI does: every file the Makefile ships
is listed, nothing listed is missing, and the recipe's files alone, in
an empty directory, byte-compile.  Run it after adding a file:

#+begin_src bash
make recipe-check
#+end_src

** Compiling one file by hand

=M-x byte-compile-file= compiles against =load-path=.  If emjupy is also
installed from an archive, =(require 'emjupy-core)= finds the INSTALLED
copy, and a module added since then is not found.  "Cannot open load
file: emjupy-remote" means that, not a fault in the file.
=make compile= puts =src/= first.  By hand, put the checkout first on
=load-path=, or uninstall the package meanwhile.

The tests, the scripts in =tools/=, =emjupy-pkg.el= and =publish.el= say
=no-byte-compile=: they are not code to load compiled.  An install from
git with package-vc, or with =use-package :vc=, compiles the whole
checkout.  Without the mark, such an install reports an error when it
compiles a test.

* Tests

** Unit tests

The self-contained suite needs only =websocket=:

#+begin_src bash
make test
# which is
emacs -batch -Q -l test/emjupy-run-tests.el
#+end_src

=websocket= comes from =load-path=, then from =EMJUPY_WEBSOCKET_DIR=,
then from GNU ELPA.  So the suite runs offline too:

#+begin_src bash
EMJUPY_WEBSOCKET_DIR=/path/to/emacs-websocket make test
#+end_src

** Integration tests (real server, real kernel, real LSP)

=emjupy-integration-test.el= runs real Python in a real kernel on a live
Jupyter server.  The tests are opt-in: they =ert-skip= unless the
environment names a running server.  They catch what only a live server
shows: an image this Emacs cannot display, a WebSocket URL that drops
its base path, or a saved notebook that no other tool opens.

| Variable           | Meaning                                                   |
|--------------------+-----------------------------------------------------------|
| =EMJUPY_TEST_URL=    | =host:port= of a running server (the LOCAL end of a tunnel) |
| =EMJUPY_TEST_TOKEN=  | its token                                                 |
| =EMJUPY_TEST_ROOT=   | server root dir, for the nbformat-validation test         |
| =EMJUPY_TEST_URL2=   | a SECOND server, for the multi-server tests               |
| =EMJUPY_TEST_TOKEN2= | its token (defaults to =EMJUPY_TEST_TOKEN=)                 |

For the *remote* path, point =EMJUPY_TEST_URL= at the local end of an ssh
tunnel:

#+begin_src bash
# server side: jupyter listens only on loopback
JUPYTER_TOKEN=abc jupyter server --no-browser --port=8888 --ip=127.0.0.1

# client side: forward a local port through ssh
ssh -N -L 18888:127.0.0.1:8888 user@remote-host &

EMJUPY_TEST_URL=127.0.0.1:18888 EMJUPY_TEST_TOKEN=abc \
EMJUPY_TEST_ROOT=/path/to/notebook/root make check
#+end_src

The WebSocket language-server tests need =jupyter-lsp= and
=python-lsp-server= where the server runs (the =pip= line above).  Those
of the local fallback need a server on this machine's =PATH= (=pylsp=,
=pyright-langserver= or =jedi-language-server=), and skip without one.

** Robustness tests

=test/emjupy-robustness-test.el= holds tests making their own inputs.
They run with =make test=, and catch what hand-written tests miss.

Faults found by fuzzing a running notebook that are not yet fixed are
[[https://github.com/mathren/emjupy/issues][issues on GitHub]].

| Test            | What it tries                                            |
|-----------------+----------------------------------------------------------|
| message order   | random interleavings of a kernel's replies and outputs   |
| random edits    | random sequences of cell commands, invariants after each |
| undo everything | random edits, then undo to the start                     |
| round-trip      | every notebook in =test_notebooks/test-corpus/=, saved and reloaded |
| hostile content | escape floods, huge SVGs, deep JSON, awkward file names  |
| leaks           | many sessions; timers, processes, hooks, tables after    |

*** Seeds

Every failure of a randomised test names its run's seed:

#+begin_example
Info: EMJUPY_FUZZ_SEED=4, case 5
Info: after (insert-above insert-below delete-char split move-down)
#+end_example

Set it to replay the run; =EMJUPY_FUZZ_ITERATIONS= sets the cases per
test, by default ten to two hundred:

#+begin_src bash
EMJUPY_FUZZ_SEED=4 EMJUPY_FUZZ_ITERATIONS=500 make test
#+end_src

Shrink a failing sequence before working on it: drop a step, and keep
the drop while it still fails.

*** Expected failures

A test of a known, unfixed fault is marked =:expected-result :failed=,
with the reason in its docstring.  The suite stays green and the fault
stays visible.  A fix then shows as an unexpected pass, which is the cue
to remove the mark.

*** The notebook corpus

=tools/make-notebook-corpus.py= writes =test_notebooks/test-corpus/=
with =nbformat=, so each notebook is valid by Jupyter's own definition.
=tools/check-roundtrip.py= compares a notebook with emjupy's save of it
(cells, sources, outputs, metadata, attachments), and validates the
save.  Without =nbformat=, the round-trip test checks only that saving
twice changes nothing.  Add a new shape to the generator, not by hand.
The generator gives each cell the same id on every run, so the corpus
changes only when the generator does.  CI fails if the committed corpus
differs from what the generator writes.

The notebooks next to it are for trying emjupy, and are kept without
outputs; CI checks that with =nbstripout --verify=.
=nbstripout --install= makes git strip them as they are committed.
=.gitattributes= names those notebooks, and not the corpus, whose
outputs are what it tests.

*** Network faults

=tools/faultproxy.py= sits between emjupy and the server.  On command it
drops connections, stalls, delays, or splits what it forwards.  The
=emjupy-int-fault-*= tests start it in front of the test server, so they
need =python3=.  By hand:

#+begin_src bash
python3 tools/faultproxy.py 127.0.0.1 8888     # prints its port and control port
echo stall | nc 127.0.0.1 CONTROL-PORT         # or sever, resume, delay 200, chunk 7, reset
#+end_src

*** Compiled files

Emacs loads a =.elc= before its =.el=, newer or not.  To see a test fail
without a fix, =make clean= first, or the test runs the compiled old code.

** Test hygiene

A unit test must give the same answer on every machine.  Two detections
would vary: the host of an SSH tunnel, read from the process list, and
whether LaTeX renders, which depends on the programs installed.
=emjupy-probe-environment= governs both.  The unit test runner binds it
to nil.  A test of the detection itself binds it to t, and stubs what
the detection examines.

- Test the key binding, not only its command.  A command bound to =DEL=
  alone is not reached in a graphical Emacs, which sends =<backspace>=.
- Do not wrap the action tested in =ignore-errors=: the error it
  swallows may be the failure.
- A stub of a function Emacs itself uses calls through for the cases the
  test is not about.
- Assert invariants rather than mechanisms, which differ between Emacs
  versions.

** Invariants

=M-x emjupy-debug-check-invariants= reports how a buffer and its cells
disagree.  It names the cell, and says whether an overlay is missing,
overlapping, out of order, or detached from its output box, or whether
it shows text that the cell does not hold.  In each case, what is
displayed and what would be saved have come apart.  Tests call it after
every operation.

** Performance

Three tests guard against regressions, not speed:

- work after every command does not grow with the notebook;
- redrawing output does not either: only the cell concerned is redrawn;
- nothing on a path run after a command touches a remote file.

The last matters most: TRAMP blocks Emacs for a round trip, paid on every
keystroke if on the per-command path.  The test asserts no such calls,
not a duration, which would depend on a network.  The costs kept small
are measured in [[file:language-server.org][Language server
support]].

* Releasing and MELPA

** Releasing

1. *Set the version.*  On GitHub: Actions, "Set version", "Run
   workflow", with the new version as =X.Y.Z=.  The workflow writes the
   version everywhere the current one is: the =;; Version:= header,
   =emjupy-version=, =src/emjupy-pkg.el=, and the sample in
   =docs/usage.org=.  It checks that they agree, and commits.  Locally:
   =make set-version X.Y.Z=.
2. *Tag that commit* with the version, and push the tag.  The release
   then runs the tests, puts the tarball on the release page, and
   publishes the site, all from that commit.  Tag it yourself: a tag
   that a workflow pushes starts no other workflow.  A commit message
   with =[skip ci]= skips tag pushes too, so tag a commit without it.

** The package's own description

=C-h P emjupy= shows the =;;; Commentary:= of =src/emjupy.el=: what
emjupy is, what it needs, and how to start.  It is written for someone
who has just installed it.  package.el would otherwise show a README, a
web page of badges and links.  So the tarball from =make package= has no
README, like MELPA's.  A =package-vc= install is the whole checkout, and
shows the README.

The opening paragraph is the same in the Commentary, the README and
=docs/index.org=; keep it so.  The one-line summary is the same in
=src/emjupy.el='s header and =src/emjupy-pkg.el=.

MELPA's default =:files= does not look.  They are listed by name, so

which the melpazoid job reads too:

Before submitting:

#+begin_src bash
make check                 # unit and integration tests
make lint                  # checkdoc and package-lint
make package               # builds the tar
#+end_src

and check that:

- melpazoid reports nothing -- its CI job runs it on the recipe above,
  warnings as errors;
- the tar installs into an empty =package-user-dir= and =M-x
  emjupy-mode= works there;
- each module loads on its own in a fresh Emacs, which shows an
  accidental dependency on load order.
