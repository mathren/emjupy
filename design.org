#+TITLE: emjupy — Design Plan
#+AUTHOR: Mathieu Renzo + Claude Sonnet 4.6

* Executive Summary

=emjupy= is a minimal, single-file Emacs package for native Jupyter notebook
editing. It connects to a running Jupyter server (local or remote via SSH
tunnel) using the Jupyter HTTP+WebSocket REST API — the same transport
browsers use — requiring no ZMQ dynamic modules, no Python subprocess, and
no external Emacs packages beyond =websocket= (GNU ELPA). It reads and writes
standard =.ipynb= JSON so notebooks are always shareable with non-Emacs users.

* Landscape Analysis

** What exists and why we don't use it

| Package        | Approach          | Fatal flaw for our goals                                                                         |
|----------------+-------------------+--------------------------------------------------------------------------------------------------|
| =ein=            | HTTP + WebSocket  | Sunset 2023; polymode + fragile overlay; no undo; no eglot                                       |
| =emacs-jupyter=  | ZMQ directly      | Needs =emacs-zmq= (dynamic module); can't connect via HTTP tunnel; notebook server hides ZMQ ports |
| =ob-jupyter=     | Org-babel wrapper | Not .ipynb-compatible; no notebook list UI                                                       |
| EIN greenfield | Overlay rewrite   | Still in early development (2025); same polymode issues                                          |

** Key insight: use the browser's transport, not ZMQ

When you run =jupyter notebook --no-browser --port=8888=, the server exposes:

- =GET  /api/kernels=          → list running kernels
- =POST /api/kernels=          → start a kernel
- =GET  /api/sessions=         → list sessions (kernel ↔ notebook pairs)
- =POST /api/sessions=         → create/attach session
- =GET  /api/contents=         → list notebooks
- =GET  /api/contents/<path>=  → fetch notebook JSON
- =PUT  /api/contents/<path>=  → save notebook JSON
- =WS   /api/kernels/<id>/channels= → Jupyter wire protocol over WebSocket

This is exactly what every browser-based client (JupyterLab, Classic Notebook)
uses. It works transparently through an SSH tunnel, survives reconnects, and
requires only =url.el= (built-in) and =websocket.el= (GNU ELPA, zero C deps).

* Layer 1 — HTTP (=url.el=, built-in)

#+begin_src emacs-lisp
;; Thin wrappers around url-retrieve-synchronously / url-retrieve
(emjupy--http-get    server path &optional callback)
(emjupy--http-post   server path body &optional callback)
(emjupy--http-put    server path body &optional callback)
(emjupy--http-delete server path &optional callback)
#+end_src

Token auth: add =Authorization: token <TOKEN>= header when token is non-empty.
For async calls pass a callback; for list UI use sync. All JSON decoded via
=json-parse-string= (built-in, Emacs 27+).

* Layer 2 — WebSocket / Jupyter Wire Protocol

** Dependency

=websocket= from GNU ELPA. Pure Elisp, no C. Already a transitive dep of
=eglot= via =jsonrpc=, so likely already installed in modern Emacs configs.

** Connection lifecycle

#+begin_src
emjupy-connect (host port token)
  → REST GET /api/kernels           ; find or create kernel
  → REST POST /api/sessions         ; bind kernel ↔ notebook path
  → websocket-open ws-url           ; open channel
     :on-open    → send kernel_info_request
     :on-message → emjupy--dispatch-message
     :on-close   → schedule reconnect (exponential backoff, 5 attempts)
     :on-error   → log + notify user
#+end_src

** Message dispatch (Jupyter wire protocol)

Messages arrive as JSON over the single WebSocket channel:

#+begin_src emacs-lisp
(defun emjupy--dispatch-message (ws frame)
  (let* ((msg   (json-parse-string (websocket-frame-text frame)))
         (ch    (gethash "channel" msg))     ; "shell"|"iopub"|"stdin"
         (type  (gethash "msg_type" msg))
         (id    (gethash "msg_id" (gethash "parent_header" msg))))
    (pcase (cons ch type)
      ;; execution results
      (`("iopub"  . "stream")          (emjupy--handle-stream msg))
      (`("iopub"  . "execute_result")  (emjupy--handle-result msg))
      (`("iopub"  . "display_data")    (emjupy--handle-display msg))
      (`("iopub"  . "error")           (emjupy--handle-error msg))
      (`("iopub"  . "status")          (emjupy--handle-status msg))
      (`("iopub"  . "clear_output")    (emjupy--handle-clear msg))
      ;; shell replies → resolve pending callbacks
      (`("shell"  . "execute_reply")   (emjupy--resolve-pending id msg))
      (`("shell"  . "complete_reply")  (emjupy--resolve-pending id msg))
      (`("shell"  . "inspect_reply")   (emjupy--resolve-pending id msg))
      (`("shell"  . "kernel_info_reply") (emjupy--handle-kernel-info msg)))))
#+end_src

** Reconnection

On =:on-close= callback: if kernel is not =dead=, schedule
=(run-with-timer delay nil #'emjupy--reconnect kernel)= with exponential
backoff (1 s, 2 s, 4 s, 8 s, 16 s). The remote kernel keeps running; only
the WebSocket is re-established. Pending callbacks are preserved in
=emjupy-kernel-pending= and re-sent after reconnect.

* Layer 4 — Buffer & Cell Rendering

** Design principle: overlays, not polymode

Each cell occupies a contiguous region in a single buffer. Overlays are used
for:
- Cell boundary markers (header line showing type + execution count)
- Output regions (text properties, =display= property for images)
- Syntax highlighting via =font-lock-fontify-region= with
  =python-mode= font-lock rules applied to code cells

This approach avoids polymode's fragility and gives standard Emacs undo.

** Buffer layout (visual)

** Cell navigation

Point moves between cells using text-property boundaries. =C-c C-n/p= jump
by cell. Within a cell, all normal Emacs motion/editing commands work — this
is a plain buffer with no mode restrictions.

* Layer 5 — Output Rendering

| Output type      | Rendering                                         |
|------------------+---------------------------------------------------|
| =text/plain=       | Inserted as-is in output overlay                  |
| =text/html=        | Stripped to plain text (optional: shr.el render)  |
| =image/png=        | =create-image= + =overlay-put= with =display= prop      |
| =image/svg+xml=    | =create-image= (SVG, built-in since Emacs 27)       |
| =application/json= | Pretty-printed via =json-pretty-print=              |
| =text/latex=       | Shown as raw LaTeX (AUCTeX users can open in buf) |
| stderr / error   | Highlighted with =error= face + traceback folded    |

Images are decoded from base64 using =base64-decode-string= (built-in) and
stored as temporary files in =temporary-file-directory=, then loaded with
=create-image=. Temporary files are cleaned up on =kill-buffer-hook=.

* Layer 6 — Completion (capf)

#+begin_src emacs-lisp
(defun emjupy-completion-at-point ()
  "CAPF function: send complete_request to kernel."
  (when-let* ((cell (emjupy--cell-at-point))
              (kernel (emjupy-notebook-kernel emjupy--notebook))
              (bounds (bounds-of-thing-at-point 'symbol)))
    (list (car bounds) (cdr bounds)
          (completion-table-dynamic
           (lambda (prefix)
             ;; Send complete_request, block briefly with accept-process-output
             (emjupy--kernel-complete kernel
               (buffer-substring-no-properties (point-min) (point))
               (point))))
          :annotation-function #'emjupy--completion-annotation
          :company-doc-buffer   #'emjupy--completion-doc)))
#+end_src

This integrates transparently with =corfu=, =company=, or the default
=completion-at-point= minibuffer UI. =orderless= works because we return
a completion table.

* Layer 7 — Eglot Integration

** Venv detection

On notebook open, query kernel info (=kernel_info_reply=) for the Python
executable path. Then:

#+begin_src emacs-lisp
(defun emjupy--setup-eglot (notebook)
  (let* ((py-exec  (emjupy--kernel-python-executable notebook))
         (venv-bin (file-name-directory py-exec)))
    ;; Prepend venv/bin to exec-path for this buffer
    (setq-local exec-path (cons venv-bin exec-path))
    ;; Point eglot at the right python
    (setq-local eglot-workspace-configuration
                `(:pylsp (:plugins (:jedi (:environment ,venv-bin)))))
    (eglot-ensure)))
#+end_src

If the kernel is on a remote host (TRAMP path), the Python executable path
is a TRAMP path and eglot's built-in TRAMP support handles the rest.

** What eglot provides on top of kernel completions

- Static type inference and cross-file symbol resolution (pylsp/pyright)
- Diagnostics / flymake integration
- =xref= go-to-definition, find-references
- Hover documentation (=eldoc=)

Kernel completions (dynamic, runtime-aware) and LSP completions (static,
type-aware) are merged automatically by Emacs's =completion-at-point=
machinery since both register as CAPFs.

* Python Bridge (=emjupy_bridge.py=)

This is a small optional helper that Emacs can invoke via =call-process= or
=make-process= to introspect the Python environment. It is not required for
basic connectivity.

#+begin_src python
#!/usr/bin/env python3
"""emjupy_bridge.py — lightweight helper for Emacs emjupy package.

Usage:
  python emjupy_bridge.py kernel-info <port> [--token TOKEN]
  python emjupy_bridge.py venv-info    <python-executable>
  python emjupy_bridge.py launch       [--port PORT] [--no-token]
"""
import sys, json, subprocess, urllib.request

def kernel_info(port, token=""):
    "Return running kernels as JSON list."
    headers = {"Authorization": f"token {token}"} if token else {}
    req = urllib.request.Request(f"http://localhost:{port}/api/kernels",
                                  headers=headers)
    with urllib.request.urlopen(req) as r:
        print(r.read().decode())

def venv_info(python_exec):
    "Return venv root and sys.path for a given python executable."
    code = "import sys,json; print(json.dumps({'prefix':sys.prefix,'path':sys.path}))"
    result = subprocess.run([python_exec, "-c", code],
                            capture_output=True, text=True)
    print(result.stdout)

def launch(port=8888, token=""):
    "Start a Jupyter server; print its URL."
    args = ["jupyter", "notebook", "--no-browser", f"--port={port}"]
    if not token:
        args += ["--ServerApp.token=''", "--ServerApp.password=''"]
    print(json.dumps({"cmd": args}))  # Emacs starts the process itself

if __name__ == "__main__":
    cmd = sys.argv[1]
    if cmd == "kernel-info":  kernel_info(sys.argv[2], sys.argv[3] if len(sys.argv)>3 else "")
    elif cmd == "venv-info":  venv_info(sys.argv[2])
    elif cmd == "launch":     launch()
#+end_src

* Key Design Decisions (Rationale)

** HTTP+WebSocket, not ZMQ

=emacs-jupyter= (dzop) uses ZMQ via a dynamic C module. This is powerful but
requires Emacs to be compiled with module support and blocks connection to
servers that only expose the HTTP API (the case for =jupyter notebook
--no-browser= and for any cloud-hosted kernel). Our approach works with any
standard Jupyter server, local or remote.

** Single =.el= file

Easier to install (git clone + =-L .=), easier to audit, easier to vendor.
All logical sections are separated by section comments and the file is
readable top-to-bottom. If it grows beyond ~2000 lines, sections become
separate files but share the =emjupy-= namespace.

** Overlays, not polymode or indirect buffers

EIN's polymode approach caused cascading bugs (broken undo, fragile
font-lock, jumpy cursor). Overlays keep a single buffer, single undo ring,
and let all standard Emacs commands work without interception. Font-lock for
code cells is applied via =font-lock-fontify-region= with the guest mode's
rules — the same technique used by org-mode source blocks.

** =websocket.el= as sole external dependency

=websocket= is on GNU ELPA, pure Elisp, used by =eglot= internally, and
maintained actively. Every other feature (JSON, HTTP, images, completions,
LSP) uses Emacs built-ins (Emacs 29+). For Emacs 27/28 compatibility a small
shim handles =json-parse-string= differences.

** Resilient reconnect

The remote Python kernel is a long-running process (holds loaded datasets).
Only the WebSocket client-side connection is fragile. On disconnect we
schedule reconnect with backoff, re-send any pending requests, and update the
mode-line indicator. Users see a brief "reconnecting…" status, not a crash.
#+end_src
